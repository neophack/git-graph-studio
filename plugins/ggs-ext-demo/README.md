# GGX Demo — the `.ggx` plugin format's worked example

This package is the reference plugin of Git Graph Studio's extension platform: one folder,
small enough to read in one sitting, that uses **every part of the format once** — two pages, a
process backend, commands, a keybinding, context-menu entries and an icon. It ships with the
app as the **bundled sample**: the Extensions view lists it even before it is installed, and
its *Install* button is one click (nothing is ever installed without that ask). New plugins —
yours, or one an AI assistant designs from this document — start from this folder.

## Try it in one minute

1. Open the **Extensions** view.
2. Find **GGX Demo** (the row marked *sample*) and press **Install the bundled sample plugin**.
   Installing means running: the backend comes up at once and the row shows its pid.
3. Run **GGX Demo: Open the Tour Page** from the command palette (or `Ctrl+Alt+G`): a guided
   tour page where every button exercises one platform capability.
4. The backend's health, restart and log live on the same row and the extension's detail page.

The package can also be built and installed by hand: `scripts\build-plugins.bat` at the
repository root packs `target\studio\bundled\ggs-ext-demo-<version>.ggx`, installable through
*Extensions: Install Extension from GGX...*.

## The package, file by file

| File | What it is |
| ---- | ---------- |
| `manifest.json` *(generated by the packer)* | The `ggx/2` header: id, version, the page registry, the backend declaration, permissions. |
| `package.json` | The VS Code-style manifest: the contributed commands, keybindings and menus the workbench's palette and context menus read. |
| `web/view.html` | The page named `main` — the tour. Plain HTML; the app composes its page bootstrap into it at serve time. |
| `web/params.html` | The page named `params` — shows the parameters it was opened with. |
| `src/main.rs` | The backend binary (`ggs-ext-demo`): one JSON line in, one JSON line out, over stdin/stdout. |
| `resources/icon.svg` | The icon the Extensions view shows. |
| `build.mjs` | The packer: zips the above into a `.ggx`. |
| `README.md` | This guide. |

## `manifest.json` — the `ggx/2` header

Written by `build.mjs`; the shape is the contract, not the script:

```json
{
	"format": "ggx/2",
	"id": "ggs.ext-demo",
	"version": "0.2.0",
	"displayName": "GGX Demo",
	"engines": { "ggs": ">=0.1.0" },
	"pages": {
		"main":   { "page": "web/view.html",   "title": "GGX Demo" },
		"params": { "page": "web/params.html", "title": "Params" }
	},
	"backend": {
		"kind": "process",
		"command": "bin/win32-x64/ggs-ext-demo.exe",
		"binaries": { "win32-x64": "bin/win32-x64/ggs-ext-demo.exe" }
	},
	"permissions": ["clipboard"]
}
```

The id is `{publisher}.{name}` and must match `package.json`, as must the version. `pages` is
every page the package can show, by id. `backend` may be omitted (a frontend-only plugin);
`command` names the build host's binary and doubles as the fallback for a platform not listed
in `binaries` (`{os}-{arch}` keys, e.g. `win32-x64`). Upgrades are forward-only like VSIX: a
newer version replaces, an equal version is refused, an older one is rejected.
`format: "ggx/1"` (a single `frontend.page`, no registry, no backend) still installs.

## `package.json` — what the workbench reads

`contributes.commands` (id + palette title), `contributes.keybindings`, and
`contributes.menus` (`explorer/context`, `editor/context`) — the same contribution points VS
Code uses, read from the installed copy at activation. **Commands declared here are the whole
UI surface of a plugin**: the palette lists them, menus bind them, keybindings fire them, and
each execution reaches your backend (below). Keep the declared list and the backend's
`initialize` answer identical — that agreement is on you, the host checks nothing.

## The backend — `ggs-ext/1` over stdin/stdout

Newline-delimited JSON-RPC 2.0: one line per message, one request answered at a time. Any
language that can write a line to stdout qualifies — this one is Rust (`src/main.rs`, built on
the app crate's `ggx_protocol::serve_plugin`), a `deno compile` binary or a Python script
behind a declared interpreter would look identical on the wire.

The host drives; the plugin answers:

| The host sends | The plugin answers |
| -------------- | ------------------ |
| `initialize` — right after spawn, with `protocolVersion`, `extensionId`, `extensionPath` | `{ "protocolVersion": "ggs-ext/1", "capabilities": { "commands": [...] } }` within 10 s |
| `runCommand` — `{ "command": "your.command.id", "args": [...] }` | `{ "result": <any JSON> }` or `{ "error": { "message": "…" } }` |
| `shutdown` (notification) — the goodbye before a deliberate kill | nothing; exit when stdin closes |

The plugin may send notifications (no id, never answered): `$/log` with `{ "message": "…" }`
is the backend's log channel, recorded by the host and shown in the Extensions view's backend
status; stderr is captured the same way (prefixed `stderr:`).

Three conventions worth knowing:

- **`openPage` is how a command surfaces UI.** A result object naming one of your own pages —
  `{ "openPage": "params", "params": { … } }` — opens it in an editor tab, with `params`
  delivered to the page's context. `ggs.ext-demo.openParams` does exactly this.
- **The process is warm.** It spawns once (at app boot, at install, or lazily on the first
  command) and stays; state survives between calls — `ggs.ext-demo.tick` counts up.
- **`GGS_INSTANCE_ID`** tells two concurrently running windows' backends apart; per-instance
  state keys on it.

A crash never takes the app with it: pending calls fail, the backend is marked dead with the
reason in its status row, and the next command starts it again. If your plugin must answer
bursts of *concurrent* requests (an engine, an indexer), declare
`"protocol": "ggx-rpc/1"` instead — a thread-per-request variant; the demo deliberately shows
the simple one every plugin should start with.

## The pages — `acquireGgsApi()`

The app serves a package's files over its `ggx://` protocol in a sandboxed iframe and composes
one bootstrap script into every HTML page: it defines `acquireGgsApi()`, the page's **only**
entry into the host (the webview's counterpart of `require('vscode')`). Call it once, then:

- **`api.ready`** — a promise resolving with `{ extensionId, pageId, params, language }`.
- **`api.request(method, args)`** — a promise; the surface every button on the tour page uses:

| `method` | `args` | Resolves with |
| -------- | ------ | ------------- |
| `backend.run` | `[commandId, argArray]` | your backend's result; **rejects** on its error |
| `pages.open` | `[pageId, params]` | `undefined` — opens a sibling page of the same package |
| `notify` | `[kind, message, buttons?]` | the clicked button's label, or `undefined` |
| `showInputBox` | `[title, initialValue?]` | the entered string, or `undefined` when dismissed |
| `showQuickPick` | `[options[], placeholder?]` | the picked label, or `undefined` |
| `commands.execute` | `[commandId, args?]` | a workbench (or another extension's) command's result |
| `commands.list` | `[]` | every registered command id |
| `clipboard.writeText` | `[text]` | `undefined` |
| `openExternal` | `[url]` | `true` |
| `settings.update` | `[key, value]` | `undefined` |
| `log` | `[label, message]` | `undefined` — the host console |

Pages render; they do not register commands (declare those in `package.json`) and cannot
escape their own directory. **Styling is the page's own** — the host injects no stylesheet, so
carry your CSS inside the package (both demo pages style themselves from one `<style>` block
and follow the system's light/dark preference).

## Lifecycle, in one paragraph

*Install means run*: the boot pass starts every installed package that declares a backend, an
install starts its backend at once, and the first command remains the lazy fallback. Multiple
app instances each spawn and own only their own backends; every backend dies on app exit, on
uninstall (before the directory is removed — a running binary cannot be deleted on Windows),
and on upgrade. Uninstalling from the Extensions view does all of this for the user.

## Building and packing

```
scripts\build-plugins.bat                 # every plugin under plugins/, from the repo root
  └─ plugins\ggs-ext-demo\build.mjs       # this plugin's own packer
       target\studio\bundled\ggs-ext-demo-<version>.ggx
```

The packer zips the manifest it derives from `package.json`, the pages, the README, the icon
and — when `--bin <path>` (or a built Cargo target) is available — the backend binary under
`bin/<platform-key>/`. `scripts\prepare.mjs` runs it as part of every app build and places a
fixed-name copy (`ggs-ext-demo.ggx`) beside the app for the installer to carry; that copy is
what the Extensions view's one-click *Install* installs.

## Writing your own plugin — the checklist

Copy this folder and rename as you go; keep each step's one-file rule.

1. **Identity.** `package.json`: new `publisher` + `name` (the id is `{publisher}.{name}`),
   a `version`, a `description`, `engines.ggs`. Prefix every command id with it.
2. **Commands.** Declare them in `contributes` (titles, keybindings, menus). That list — and
   nothing else — is what the workbench shows.
3. **Backend** (`src/main.rs` or any binary): answer `initialize` with the same command list;
   answer each `runCommand`; return `{ "openPage": … }` to surface a page; send `$/log` lines;
   keep state in process variables. Omit the backend entirely for a frontend-only plugin.
4. **Pages** (`web/*.html`): plain documents; `acquireGgsApi()` once; drive everything through
   `api.request`; style yourselves; read open `params` from `api.ready`.
5. **Pack** with a copy of `build.mjs` (it is ~40 lines; the shared zip writer lives in
   `scripts/build-ggx.mjs`), install the `.ggx`, and exercise it from the palette.
6. **Document**: your README renders on the extension's detail page — say what the plugin
   does, which permissions it wants and why.

This file is deliberately a complete specification-by-example: a human — or an AI assistant
asked to "design a new plugin for Git Graph Studio" — can build a correct package from it
plus the sources beside it, without reading the app's own code.
