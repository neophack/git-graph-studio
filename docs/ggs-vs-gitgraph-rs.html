两个仓库各自是什么What each repo is

vscode-git-graph-rs/git 子模块 · 独立仓库

VS Code 扩展 git-graph-rs 本体，GGS 对它只消费、不修改：
  • webview 前端 — media/out.min.js / out.min.css、web/ 样式（编译产物，原样使用）
  • 扩展宿主代码 — src/config.ts（配置组合）、src/comparisonView.ts（比对页生成器）等
  • Rust 引擎 — native/core 即 git-graph-core：基于 gix 的提交图 / 状态 / diff / 统计读引擎

git-graph-studio（GGS）宿主 · 本仓库

Tauri 2 桌面应用（VS Code 级壳：资源管理器、源代码管理、编辑器、终端…），在 Git Graph 模块里扮演 VS Code 的两个角色：
  • 扩展宿主 — src/graphHost.ts 组装 initialState、提供 acquireVsCodeApi shim、应答视图请求
  • 数据源 — src-tauri/src/cmd_graph.rs 把视图协议转给进程内引擎（读）和 git CLI（写）
一句话关系：构建期，GGS 把子模块的前端资产拷进应用、把它的 Rust 引擎链接进进程；运行期，用 view.html + shim 原样驱动它的 webview，读写分别走进程内 git-graph-core 与 git CLI —— 扩展一行不改，却在独立桌面应用里完整运行。

接缝规则：为什么乱不了Seam rules (build-enforced)

一种语言，一个文件

  • TypeScript 侧 — 只有 src/graphHost.ts 可能调用 graph_request、命名 gitgraph/ 资产路径
  • CSS 侧 — 只有 static/gitgraph/view.html 引用扩展样式（out.min、web/styles）
  • Rust 侧 — 只有 cmd_graph.rs 调 git-graph-core

读写分离

  • 读（提交 / 引用 / 详情 / 配置）— 一律进程内 gix 引擎，不起子进程
  • 写（stage / commit / fetch / push…）— 一律 git CLI，且只经 git.rs 一个出口
  • 子模块自身的提交、修改永远留在 vscode-git-graph-rs/ 里，不进本仓库
构建期强制：scripts/check-seams.mjs（每次 build / test 运行）与 src-tauri/build.rs（Rust 对应检查）扫描全仓库 —— 在 graphHost.ts / view.html / cmd_graph.rs 之外出现 graph_request、gitgraph/、out.min 等引用即 编译失败。 接缝是合同，不是习惯。

低耦合调用：最少调用怎么写Minimal-caller pattern — how new code reaches the plugin

1处 invoke('graph_request')，在 graphHost.ts，全应用唯一
1个 Rust 文件消费引擎（cmd_graph.rs；lib.rs 仅注册命令）
2个对外函数：graphRequest（读）/ runGraphAction（写）
4个窄接口导入方（见下表）
0处资产路径 / 协议细节泄漏到接缝之外

最少调用：读、写各一个函数

// 写命令（fetch / push / merge…）：一个函数 = 一整轮协议
import { runGraphAction } from './graphHost';

await runGraphAction(
	{ command: 'fetch', repo },         // 调用方只需命令名 + 参数
	{ settings, confirm: askUser }    // lossWarning 确认环在内部处理
);

// 读命令（commitDetails / compareCommits…）：单次往返
const resp = await graphRequest(
	{ command: 'commitDetails', repo, commitHash }
);
iframe、postMessage、Tauri IPC、写命令串行排队、错误规约 —— 全部在 graphHost.ts 内侧；调用方一个 import 一个函数，不含任何协议知识。

现有调用方的依赖面（实测就是这么窄）

workbench.tsGraphHost组合根：挂载视图、实现 GraphHostDelegate
editor.tsCompareHostCommit Comparison 标签页
gitCommands.tsrunGraphActionGit 菜单的全部写命令复用同一通道
fileHistory.tsgraphRequestTimeline 视图的提交读取
反向同样解耦：插件调 shell 走 GraphHostDelegate（openFile / openDiff / runInTerminal / repoChanged…），插件也不知道编辑器与终端的存在 —— 双方只认识消息。
为什么这就是“最少”：协议的「命令名 + 参数对象」是调用方唯一必须共享的知识，再往下没有可删的依赖了 —— 更低只能改成经 commands.ts 命令注册表间接寻址，多一层抽象却不减少任何真实调用。 新代码直接 invoke('graph_request') 会被 check-seams.mjs 构建期拦下；正确姿势永远是经 graphHost.ts 的导出。要新增能力：请求在 handleLocally 加 case，动作走命令注册表。
