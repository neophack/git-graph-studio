## 1. 结论摘要

现有 Hub 在"防扫描、防滥用、防冒充 PC"方面已经做得比较完整：无应答的静默门、挑战签名、限速、访客上限、黑名单、审计。但在"加密"和"用户之间不冲突"两项上有根本缺口：

1. **Hub 能看到全部明文**：端到端加密只写了密码学核心，没有接入。登录密码、会话 Cookie、文件内容、Claude 对话，对 Hub 运营者全部可见（§2 的 H1）。
2. **已写好的加密核心本身有缺陷**：两个方向共用一把密钥，nonce 随机，不认证帧头，没有序号。恶意的 Hub 可以重放、反射或调换加密帧，例如把一次"发送给 Claude"或"git push"重放一遍。也没有前向保密（H2）。
3. **路径式链接下，所有 PC 共用一个浏览器源**：一台 PC 的主人（或者装在那台 PC 上的扩展）能在受害者的浏览器里，以同源身份读取并操作另一台 PC 的远程页面。这不是 XSS，是共源结构造成的，现有的存储前缀和请求头校验挡不住（H3）。

本计划的对策：

| 要求 | 对策 |
| ---- | ---- |
| 安全加密 | 端到端加密 v2：Noise NK 握手，带前向保密；按方向分开密钥，用计数器作 nonce，认证帧头，拒绝重放和乱序；登录与会话绑定在加密通道上；经 Hub 时强制开启（§4） |
| 用户之间不冲突 | 每台 PC 一个独立的源：`https://<uuid>.relay.example.com/`；Cookie 用 `__Host-` 前缀；每条隧道限带宽并公平调度（§5、§7） |
| 防攻击 | 保留现有的全部防护，新增：带宽公平、全局内存预算、每 IP 并发上限、重连风暴抑制、模糊测试、对抗性中间人测试（§7、§12） |
| 接口简单 | 对外只有两个入口：链接和 `/tunnel`；管理只通过服务器本机的命令行，网络上没有管理接口（§10） |
| 使用简易 | 部署者三条命令；PC 主人粘贴一串连接码；远程用户扫码、输入密码，可以"记住此设备"（§9） |

需要如实说明的一点：网页应用的代码是经 Hub 送到浏览器的。一个**主动作恶**的 Hub 可以篡改页面代码，在加密之前窃取密码。纯网页应用无法从根本上防住这一点。端到端加密完全防住的是**被动**的 Hub：好奇的运营者、日志泄露、被入侵后只读的服务器、反向代理或 CDN 的记录。对主动作恶的 Hub，本计划提供检测与纵深防护（§4.7），并明确建议：不信任运营者的用户，自建 Hub 或用局域网、VPN 直连。

## 2. 现状核查

| # | 现状 | 问题 | 位置 |
| - | ---- | ---- | ---- |
| H1 | 端到端加密只落地了密码学核心和跨实现测试向量，没有接入任何收发路径 | 经 Hub 的全部流量对 Hub 明文可见，包括登录密码、会话 Cookie、文件、终端和 Claude 对话（ggs-remote-plan.md §23.7 已如实声明） | `daemon/src/e2e.rs`、`src/remote/e2e.ts` |
| H2 | 加密核心：浏览器临时 X25519 × PC 静态 X25519 → HKDF → **一把** AES-256-GCM 密钥，两个方向共用；12 字节**随机** nonce；没有关联数据（AAD），帧头不受认证；没有序号 | (a) 重放：Hub 把截获的加密帧再发一次，PC 照常解密执行；(b) 反射：同一把密钥两个方向通用，PC 发出的帧可以被送回 PC；(c) 调换与丢弃：没有序号就无法发现；(d) 帧头可改：Hub 改动帧类型或流 id，不会被发现；(e) 没有前向保密：PC 静态私钥日后泄露，所有截获的历史会话都能解开；(f) 随机 nonce 对同一密钥的使用次数有上限（约 2³²） | `e2e.rs` 的 `conversation_key`、`seal`、`wrap_frame`；文件头注释仍写着旧的 secretbox 和 24 字节 nonce，与代码不符 |
| H3 | 链接是 `https://hub/u/<uuid>/`，所有 PC 共用一个源。隔离靠 Cookie 的 `Path`、存储键前缀、`X-GGS-Base` 请求头 | 浏览器的同源策略按源判断，不认路径。PC A 提供的页面里只要有一段脚本以 Hub 源运行（被改过的守护进程，或 A 上装的扩展的 webview：srcdoc iframe 带 `allow-same-origin` 时继承 Hub 源），就能：`window.open('/u/B/')` 拿到同源窗口引用，直接读 B 页面的 DOM 和内存；或者 `fetch('/u/B/…')`，浏览器自动带上 B 的 Cookie，`X-GGS-Base` 也能伪造。ggs-remote-plan.md §20.6.1 的"剩余风险只在工作台自身出现 XSS 时存在"的判断不成立 | `daemon/src/http/*`、`hub/src/http_proxy.rs`、`src/remote/storage.ts` |
| H4 | 接入控制只有一个全服务器共享的 `join_key` | 不能单独撤销某一台 PC，只能更换口令并重新发给所有人；口令一旦泄露，任何人都能接入 | `hub/src/config.rs`、`tunnel.rs` |
| H5 | 资源限制有每条隧道的并发会话数和可选的每日流量，但没有速率限制和公平调度 | 一台 PC 的大文件下载可以占满 Hub 的出口带宽，拖慢其他所有用户 | `hub/src/state.rs`、`http_proxy.rs` |
| H6 | 自带的 Caddy 配置没有 HSTS | 首次访问可能被降级到 HTTP | `hub/deploy/Caddyfile` |
| H7 | 部署要手写 `hub.toml` 和 `Caddyfile`；连接码 `ggsr1:` 里带的是共享 `join_key`；`T_REPLACED` 以后 PC 停止重连，只在插件页上提示 | 对普通用户来说门槛偏高，出错时也看不出原因 | `hub/deploy/*`、`extension.js` 的远程访问页 |
| H8 | 下载、上传、扩展资源都走 HTTP 路由 | 接入端到端加密后，浏览器自带的下载功能无法解密密文，需要另行设计（§4.6） | `daemon/src/http/*` |

已经做到、本计划保留的部分：

- uuid 由设备公钥哈希得出，接入时必须签 Hub 的一次性挑战，并绑定 Hub 主机名；
- 静默门：链接和 `/tunnel` 之外的路径一律无应答；
- 握手与 HTTP 限速，不在线链接的探测封禁，每条链接的每日访客上限；
- 请求头读取超时、请求体空闲超时、会话槽在请求被放弃时回收、应答头 30 秒超时；
- 审计日志（不记录正文，令牌脱敏）、黑名单（30 秒热加载）、跨 PC 缓存只收公开的不可变构建资源；
- 守护进程页面的 CSP（`frame-ancestors 'none'`）和 `Referrer-Policy: no-referrer`。

## 3. 威胁模型

| 攻击者 | 能力 | 本计划之后的结果 |
| ------ | ---- | ---------------- |
| **扫描者** | 扫描端口和路径，猜测链接 | 只看到 TLS 握手，任何 HTTP 请求都无应答；122 位的 uuid 无法枚举（已有） |
| **暴力破解者** | 知道链接，猜密码 | Hub 按 IP 和 uuid 限制握手次数；PC 用 Argon2id 校验并逐步锁定；强制最短密码长度并拒绝常见密码（§7.3） |
| **其他租户** | 自己有一台 PC 接在同一个 Hub 上，能控制自己 PC 提供的全部内容 | **子域名模式下无法触及别的 PC**：不同源，同源策略生效，Cookie 用 `__Host-` 前缀（§5）。路径模式下仍有 H3 的风险，因此路径模式只用于互相信任的人，部署向导会给出警告 |
| **被动的 Hub** | 运营者好奇、日志或磁盘泄露、服务器被入侵但只能读、TLS 终止点（Caddy、CDN）有记录 | **看不到任何内容**：没有密码、Cookie、文件、对话。只能看到元数据：IP、时间、流量大小、哪个 uuid 在线（§4） |
| **主动作恶的 Hub** | 篡改、重放、丢弃、调换帧；替换服务端身份密钥；篡改发给浏览器的网页代码 | 篡改、重放、调换、反射：全部被发现并断开（§4.3）；替换身份密钥：被 uuid 与公钥的绑定识破（已有）；**篡改网页代码：无法从根本上阻止**，只能检测与纵深防护（§4.7） |
| **网络中间人** | 位于浏览器和 Hub 之间，或 PC 和 Hub 之间 | TLS 加 HSTS；PC 端校验证书，自签证书的 Hub 用指纹固定（已有）；再加上端到端加密，等于两层加密 |
| **拿到手机的人** | 手机丢失或被借走 | "记住此设备"使用不可导出的设备密钥；PC 端的设备列表可以一键撤销（§4.4） |
| **偷到 Cookie 的人** | 通过 XSS、恶意浏览器扩展或日志拿到 Cookie | **单凭 Cookie 什么也做不了**：每个请求都要在加密通道内，并且要出示设备密钥（§4.4） |

不在本计划范围内的：PC 本身被入侵、浏览器所在设备被植入木马、流量分析（帧大小和时间规律）。

## 4. 端到端加密 v2

### 4.1 设计选择

- **握手**采用 Noise 协议框架的 **NK** 模式：`Noise_NK_25519_AESGCM_SHA256`。浏览器事先知道 PC 的静态公钥，经 uuid 绑定验证；双方各出一把临时密钥。NK 的优点：一次往返完成；有前向保密（`ee` 项）；浏览器不需要长期身份。
- **为什么用 Noise 而不是自己设计**：它是成熟的、经过形式化分析的协议（WireGuard、WhatsApp、Lightning 都在用）。Rust 端直接用 `snow` 库；浏览器端用约 200 行代码实现 NK，复用已有依赖：tweetnacl 提供 X25519，WebCrypto 提供 AES-GCM 和 SHA-256。两端用 `snow` 生成的测试向量逐字节互证。
- 现有的 v1 核心（单一密钥、随机 nonce）从未接入，直接由 v2 取代，不做兼容。

### 4.2 身份链

```text
设备 Ed25519 公钥 ed_pub ──哈希──▶ uuid（就是链接本身）
      │
      └─签名─▶ "ggs-remote-e2e/2" ‖ x_pub ‖ not_after     （PC 的 Noise 静态公钥，有有效期）
```

- 浏览器从链接得到 uuid，从 `E2E_PARAMS` 得到 `ed_pub`、`x_pub`、签名和有效期。依次检查：`uuid_for(ed_pub) == uuid`、签名有效、尚未过期。任何一项不通过，就拒绝继续并显示红色警告，不会输入密码。
- PC 的 Noise 静态密钥每 30 天轮换一次，由设备密钥重新签名，链接不变。
- "更换链接"会同时更换设备密钥和静态密钥，旧链接立即失效（已有行为）。

### 4.3 传输层

| 项 | 规定 |
| -- | ---- |
| 密钥 | 握手结束后，Noise `Split()` 得到两把密钥：浏览器到 PC 一把，PC 到浏览器一把 |
| nonce | 每个方向一个 64 位计数器，从 0 开始，每帧加 1（Noise 标准） |
| 重放与乱序 | 接收方要求计数器严格递增；任何回退或跳号都按攻击处理：关闭连接，记录 `e2e-violation`，界面显示"连接被篡改，已断开" |
| 帧头认证 | 20 字节帧头里 Hub 需要改写的只有会话 id 字段，其余字段（类型、标志、流 id、长度）全部作为 AAD，参与认证 |
| 封装 | 外层帧头加 `FLAG_ENCRYPTED(0x40)`；载荷为 `AESGCM(k, n, AAD = 帧头中除会话 id 外的部分, 原帧载荷)`。nonce 由双方的计数器隐式得出，不在线路上传输，每帧比 v1 省 12 字节 |
| 断线续传 | 120 秒恢复窗口内重连时，双方的计数器从断开处继续，不重新握手；恢复缓冲中保存的是密文。超出窗口则重新握手 |
| 重新换钥 | 每个方向每 2²⁰ 帧或 1 GiB 数据执行一次 Noise `Rekey()` |
| 压缩 | 先压缩、后加密，每帧单独压缩，不共享字典。登录和换钥帧不压缩，避免类似 CRIME 的长度泄露 |
| 强制 | 经 Hub 的连接上，第一对帧必须是 Noise 握手；之后 PC 收到任何未加密的帧都直接断开。局域网直连已有 TLS 保护，端到端加密默认关闭，可以在设置里打开 |

### 4.4 登录与会话绑定

- **登录**：密码在加密通道内发送，帧为 `LOGIN { password, remember }`。PC 照旧用 Argon2id 校验。取代 v1 设计中独立的 `api/e2e-login` HTTP 路由。
- **会话**：登录成功后，PC 把会话绑定到这次握手的哈希 `h`。会话的每个请求都必须在这条加密通道内到达，Cookie 不再是凭据，经 Hub 时根本不设置。
- **记住此设备**：浏览器用 WebCrypto 生成一把**不可导出**的 ECDSA P-256 密钥，存进 IndexedDB（脚本拿不到私钥本身）。登录时把公钥登记到 PC，有效期 30 天。之后打开链接时，在加密通道内对 `h` 签名，签名有效即登录，不必再输密码。
- **撤销**：PC 端"远程访问"页的设备列表（已有）里删除某台设备时，同时删除它登记的公钥，这台设备的连接立即断开。
- **浏览器支持**：P-256 签名与不可导出密钥在 Chrome、Edge、Firefox、Safari（含 iOS）上都可用。隐私模式下 IndexedDB 不可写时，退回为每次输入密码。

### 4.5 什么需要加密

| 类别 | 例子 | 处理 |
| ---- | ---- | ---- |
| **公开** | 工作台构建产物（`/v/<ver>/assets/*`）、登录页外壳、`sw.js`、`manifest.webmanifest`、图标、离线页 | 明文传输，Hub 可以缓存；完整性见 §4.7 |
| **私有** | 所有 API、文件内容、目录列表、终端、Claude 对话、搜索结果、扩展资源、缩略图、下载、上传 | **只走加密通道**：WebSocket 帧，或 §4.6 的 Service Worker 解密流。经 Hub 时，PC 对私有 HTTP 路由的明文请求一律返回 403 |

### 4.6 下载、上传与扩展资源

- **下载**：页面向 Service Worker 登记一个虚拟 URL，如 `./x/<一次性 id>`，并通过 `MessageChannel` 把这次下载专用的派生密钥交给 Service Worker（只在内存里）。浏览器访问这个 URL 时，Service Worker 经加密通道取回密文，边解密边作为 `ReadableStream` 返回，响应带 `Content-Disposition: attachment`。浏览器自带的下载管理器照常工作，支持大文件。
- **没有 Service Worker 时**（极少见：经 Hub 时证书是受信任的）：在页面内取回数据并解密成 Blob，再触发下载，单个文件上限 512 MB。超过上限时提示用户改用局域网或打包下载。
- **上传**：分块上传本来就走 WebSocket 帧（`fs_write_chunk`），自然得到加密。
- **扩展 webview 的资源**：经同一个 Service Worker 解密，路径保持 `ggs/<令牌>/…`，扩展代码不需要任何改动。

### 4.7 面对主动作恶的 Hub：网页代码的完整性

纯网页应用的代码由服务器（这里是 Hub）提供，所以无法从根本上防止代码被篡改。本计划采取以下纵深措施，并在文档和界面上如实说明：

1. **入口完整性**：登录页外壳中的脚本标签都带 SRI 哈希。如果 Hub 替换了脚本但没改页面，浏览器拒绝执行。
2. **清单签名**：每个构建的资源清单（所有懒加载块的哈希）由 PC 的设备密钥签名，在加密通道内下发。加载器在执行懒加载块之前先核对哈希，不一致就停止并报警。
3. **Service Worker 固定**：首次在可信环境（局域网直连）登录过的浏览器，Service Worker 会记住构建清单的签名。之后经 Hub 访问时，如果收到的代码与已签名的清单不一致，就显示"此页面代码与你的 PC 不一致，可能被中继篡改"，并且不发送密码。局限：浏览器更新 `sw.js` 时不经过旧的 Service Worker，所以这只能拦住大部分篡改，不是全部。
4. **运营建议**：不信任 Hub 运营者的用户，应自建 Hub，或使用局域网、VPN 直连。远程访问页的说明里写明这一点。

### 4.8 性能指标

- 加密吞吐量：桌面浏览器不低于 50 MB/s，手机不低于 15 MB/s（WebCrypto 的 AES-GCM 由硬件加速）。
- 握手耗时：本地计算不超过 20 ms，加上一次网络往返。
- CPU 开销：在 remote-client-plan.md §7.4 的流量场景下，加密带来的额外 CPU 时间低于总耗时的 5%。
- 这些指标由 `scripts/probes/hub-load.mjs` 和新的浏览器基准测量，结果写入 `metrics.json` 的 `remote.e2e`。

## 5. 多用户隔离：每台 PC 一个独立的源

### 5.1 子域名模式（新部署的默认）

- 链接为 `https://<uuid>.relay.example.com/`，例如 `https://3f9c2a6e-8b1d-8c7a-9e45-2d6f0b8a71c3.relay.example.com/`。uuid 共 36 个字符，没有超过 DNS 标签的 63 字符上限。
- **DNS**：添加一条泛解析 `*.relay.example.com`。
- **证书**：一张泛域名证书。Caddy 通过 DNS-01 验证自动申请，常用 DNS 服务商都有现成插件（Cloudflare、阿里云 `caddy-dns/alidns`、腾讯云 `caddy-dns/tencentcloud`、DNSPod）。部署向导（§9.1）自动生成对应配置。
- **Hub 的路由**：按 `Host` 头取出 uuid。`Host` 不是"uuid 加配置域名"这个形态的，一律按静默门处理，不应答。
- **Cookie**：只在局域网直连时使用，名为 `__Host-ggsr`（`Secure`、`Path=/`、不设 `Domain`）。`__Host-` 前缀保证任何兄弟子域都不能设置或覆盖它。经 Hub 时不设 Cookie（§4.4）。
- **存储与 Service Worker**：按源天然隔离。现有的 `installScopedStorage` 前缀保留，用于路径模式。
- **专用域名**：Hub 应使用专门的域名，例如 `relay.example.com`，上级域名下不要部署能设置 `Domain=` Cookie 的其他应用，否则可以把 Cookie 塞给所有子域。部署向导会提示这一点。

### 5.2 路径模式（保留，只用于互相信任的人）

- 保留现有的 `/u/<uuid>/` 链接，用于个人或家庭部署，好处是不需要泛解析和泛域名证书。
- 部署向导和 Hub 启动日志都会警告："路径模式下，同一 Hub 上的用户可以互相访问对方的远程页面；只在用户互相信任时使用。"
- 开启子域名模式以后，路径式链接返回 301，重定向到子域名链接。任何形态合法的 uuid 都同样重定向，不泄露它是否在线。

### 5.3 其他可能冲突的地方

| 资源 | 隔离方式 |
| ---- | -------- |
| 链接与身份 | uuid 由各自的设备密钥决定，不可能撞车（122 位） |
| 同一把密钥在两台 PC 上 | 后连上的生效，旧的收到 `T_REPLACED`（已有）。改进：远程访问页明确提示"此链接已在另一台电脑上使用（主机名）"，并提供"在此电脑上接管"按钮，而不是停在那里 |
| 带宽 | 每条隧道一个令牌桶，Hub 的发送端在隧道之间公平调度（§7.2） |
| 缓存 | 只缓存公开的不可变构建资源，键为（版本、路径、sha256）（已有）。经子域名访问时，按内容哈希共享，与源无关 |
| 黑名单与撤销 | 按 uuid 或设备，只影响这一台 PC |
| 日志 | 审计日志按 uuid 记录，运营者可以按 uuid 导出或删除 |

## 6. 接入控制：邀请制

### 6.1 三种模式

`access` 配置项的取值：

| 模式 | 含义 | 适用 |
| ---- | ---- | ---- |
| `invite`（新部署的默认） | 每台 PC 凭一张邀请码首次接入，接入后 Hub 记住它的设备公钥，以后不再需要任何口令 | 公开部署，给多个人用 |
| `key` | 现有的共享 `join_key` | 兼容旧部署 |
| `open` | 任何 PC 都能接入，受限速与访客上限约束 | 仅限个人试用；启动时打印警告 |

### 6.2 命令行

管理只能在服务器本机执行，网络上不提供管理接口：

```text
ggs-remote-hub invite [--note 张三] [--ttl 7d] [--uses 1]
    → 打印连接码 ggsr2:https://relay.example.com#inv=<令牌>，并在终端画出二维码
ggs-remote-hub devices                 列出已接入的 PC：uuid、备注、接入时间、最近在线、今日流量
ggs-remote-hub revoke <uuid|备注>       撤销一台 PC：立即断开它的隧道，以后的握手返回 T_REJECTED{revoked}
ggs-remote-hub block <uuid>            加入黑名单（已有，用于处理滥用）
ggs-remote-hub status                  在线隧道数、会话数、带宽、内存
ggs-remote-hub doctor                  检查配置、DNS、证书、端口、时间同步，逐项显示通过或失败
```

### 6.3 存储

- 邀请：`state/invites.json`，只保存令牌的 SHA-256、有效期、剩余次数、备注。
- 设备：`state/devices.json`，每台 PC 一条记录：公钥、uuid、备注、接入时间、最近在线。
- 文件权限 0600，属于 Hub 运行用户；写入时先写临时文件再改名（原子写）；进程启动时读取，命令行修改后通知进程重新加载（`SIGHUP`，或 30 秒轮询，与黑名单相同）。
- 不引入数据库：几千台 PC 的记录不过几百 KB。
- 邀请令牌 128 位随机，比较时用常量时间。

### 6.4 握手的变化

`T_HELLO` 新增可选字段 `invite`。Hub 的处理：

- 设备已在名单里：只验证挑战签名（与现在相同）。
- 设备不在名单里：要求邀请码有效，验证通过后登记设备，并把邀请的剩余次数减 1。
- 失败原因用 `T_REJECTED` 的新取值表示：`revoked`、`invite-expired`、`invite-used`、`invite-required`。

## 7. 防攻击与资源公平

### 7.1 防护清单

| 攻击 | 措施 | 状态 |
| ---- | ---- | ---- |
| 端口与路径扫描 | 静默门：只有链接和 `/tunnel` 的握手形态才会被应答 | 已有 |
| 枚举链接 | 122 位 uuid；不在线与不存在的链接返回同一页面；探测封禁 | 已有 |
| 握手洪泛 | 每 IP 每分钟 10 次 `T_HELLO` | 已有 |
| **重连风暴** | 同一把设备密钥两次握手至少间隔 1 秒，否则返回 `T_REJECTED{retry-after}`；PC 端遵守并做指数退避 | 新增 |
| 慢速攻击（slowloris） | 请求头读取超时、请求体空闲超时、请求工作量上限 | 已有 |
| **单 IP 占用大量连接** | 每 IP 最多 16 个并发 WebSocket，最多 64 个并发 HTTP 请求 | 新增 |
| **超大帧或超大请求头** | 单帧上限 1 MiB，HTTP 请求头上限 32 KiB，超出即关闭连接 | 新增（补齐上限） |
| **内存耗尽** | 全局缓冲预算（默认 512 MiB）：超出时新会话收到 503，不影响已有会话；每条隧道 8 MiB 发送缓冲（已有） | 新增全局预算 |
| 放弃的请求占满会话槽 | `SessionSlot` 在请求结束时无论如何都回收 | 已有 |
| 当成免费网页托管 | 每链接每日访客上限、HTTP 速率、审计、黑名单 | 已有 |
| 暴力破解密码 | Hub 限制每 IP 每 uuid 每分钟 10 次 Noise 握手（启用加密后 Hub 看不到登录内容，所以按握手计数）；PC 端 Argon2id 加逐步锁定 | Hub 侧改为按握手计数 |
| 弱密码 | §7.3 | 新增 |
| 加密帧的篡改、重放、反射 | §4.3 | 新增 |
| TLS 握手洪泛 | Caddy 加操作系统的 SYN cookies；附带 fail2ban 过滤规则，读审计日志 | 新增规则文件 |

### 7.2 带宽公平

- 每条隧道一个令牌桶：`bandwidth_per_tunnel`，默认下行 8 MB/s、上行 4 MB/s，可以按设备单独覆盖（在 `devices.json` 里设置）。
- Hub 的发送端在隧道之间用**赤字轮转（DRR）**调度，单个大下载无法饿死其他隧道。
- 每日总量上限 `bytes_per_day_per_tunnel` 保留（已有）。
- **验收**：压测中一条隧道持续满速下载，另一条隧道上交互帧的 p95 延迟增加不超过 30 ms（§12）。

### 7.3 密码要求（在 PC 上设置时检查）

- 最短 10 个字符。
- 拒绝最常见的 10 000 个密码。列表压缩后约 40 KB，随守护进程发布。
- 设置界面显示密码强度条。
- 以后可以加 TOTP 二次验证作为可选项，本期不做（§15）。

## 8. 运维安全

| 项 | 规定 |
| -- | ---- |
| HTTPS | Caddyfile 加上 `Strict-Transport-Security: max-age=31536000`；只允许 TLS 1.2 及以上（Caddy 默认） |
| 进程 | systemd 单元（已有）保持 `NoNewPrivileges`、`ProtectSystem=strict`、`PrivateTmp`、`ReadWritePaths` 只放行 `state/` 和日志目录；容器以非 root 运行、根文件系统只读、`cap_drop: ALL`、默认 seccomp |
| 网络暴露 | Hub 只在本机或 Docker 内网上监听，由 Caddy 对外；`metrics` 和 `healthz` 只监听回环地址（已有） |
| 依赖 | CI 对 Hub 和守护进程运行 `cargo deny`（许可证、已知漏洞、重复依赖）和 `cargo audit`；新增依赖需要说明理由 |
| 发布 | 可复现构建；`SHA256SUMS` 附 GPG 签名（已有）；容器镜像按摘要固定 |
| 日志 | 审计日志默认关闭；开启时不记录正文、Cookie 和令牌（已有），按天轮转，默认保留 7 天；启用加密以后，Hub 本来也看不到内容 |
| 模糊测试 | `cargo-fuzz` 目标：Hub 的帧解析、msgpack 消息解码、HTTP 请求头解析、uuid 与 `Host` 解析；守护进程的加密帧解封、Noise 握手消息。CI 每晚每个目标运行 10 分钟，发现的输入加入回归语料 |

## 9. 易用性：三类人的流程

### 9.1 部署者（三条命令）

```text
$ ggs-remote-hub init --domain relay.example.com --dns alidns
  → 询问 DNS 服务商的 API 密钥（只写入 Caddy 的环境文件，权限 0600）
  → 生成 hub.toml（access = invite、子域名模式、安全默认值）、Caddyfile、docker-compose.yml
$ docker compose up -d                      （或 deb 包：systemctl enable --now ggs-remote-hub）
$ ggs-remote-hub doctor                     → 逐项显示：DNS 泛解析 ✓、泛域名证书 ✓、443 端口 ✓、时间同步 ✓
$ ggs-remote-hub invite --note 张三          → 连接码和二维码，发给张三
```

- 不给 `--dns` 时，向导采用路径模式，并打印 §5.2 的警告。
- 现有的 Docker、deb、Windows zip 三种发布形态（`hub/deploy/`）都带上 `init` 和 `doctor`。

### 9.2 PC 主人（一步）

GGS → 远程访问 → "通过服务器访问" → 粘贴连接码，或者用手机扫部署者给的二维码再复制过来 → 点"连接"。

- 连接成功后，页面显示专属链接和二维码，并标注"🔒 端到端加密"。
- 失败时用一句话说明原因和下一步：

| `T_REJECTED` 原因 | 显示 |
| ----------------- | ---- |
| `invite-expired` | 邀请码已过期，请向服务器管理员要一张新的 |
| `invite-used` | 邀请码已被使用，请向服务器管理员要一张新的 |
| `revoked` | 这台电脑已被服务器管理员移除 |
| `capacity` | 服务器已满，请稍后再试或联系管理员 |
| `version` | 服务器版本过旧，请联系管理员升级 |
| `retry-after` | 不显示，自动等待后重试 |

- 链接被另一台电脑接管（`T_REPLACED`）时：显示接管方的主机名，并提供"在此电脑上接管"按钮。

### 9.3 远程用户（扫码即用）

1. 扫 PC 页面上的二维码，打开链接。
2. 登录页显示 PC 名称和"🔒 端到端加密 · 已验证这台 PC 的身份"。身份校验不通过时，显示红色警告，并且不提供密码输入框。
3. 输入密码，勾选"记住此设备 30 天"（默认勾选）。
4. 之后再打开链接就直接进入。
5. 远程客户端的远程指示器（remote-client-plan.md §5.5）上同样显示 🔒；点击可以查看 PC 身份指纹、连接方式（Hub 或局域网）和加密状态。

## 10. 接口规范

### 10.1 Hub 对外的全部接口

| 入口 | 形态 | 其他一切 |
| ---- | ---- | -------- |
| 链接 | `https://<uuid>.<域名>/*`（子域名模式）或 `https://<域名>/u/<uuid>/*`（路径模式） | 无应答（静默门） |
| 隧道 | `wss://<域名>/tunnel`，只接受守护进程发出的那种 WebSocket 握手 | 无应答 |
| 监控 | `metrics_listen` 上的 `/metrics` 与 `/healthz`，只监听回环地址 | — |

管理只通过服务器本机的命令行（§6.2）。

### 10.2 隧道协议 v2（相对 ggs-remote-plan.md §20.4 的变化）

| 帧 | 变化 |
| -- | ---- |
| `T_HELLO` | `proto: 2`；新增可选的 `invite` |
| `T_READY` | 新增 `linkStyle: "subdomain" \| "path"`；`publicBase` 按链接形态给出 |
| `T_REJECTED` | `reason` 新增 `revoked`、`invite-expired`、`invite-used`、`invite-required`、`retry-after`（附 `retryAfterMs`） |
| `CONN_OPEN` | 新增 `host`（子域名模式下的完整主机名），守护进程据此生成页面中的绝对地址 |

过渡期内，Hub 同时接受 v1 和 v2，由 `min_proto` 配置决定，默认 1；等所有 PC 都升级以后改为 2。

### 10.3 浏览器与 PC 之间（经 Hub 时）

WebSocket 上的帧顺序：

```text
→ E2E_HELLO   { noise_msg1 }                    浏览器：e, es
← E2E_ACCEPT  { noise_msg2, params }            PC：e, ee；params = ed_pub、x_pub、签名、有效期
→ （加密）HELLO / LOGIN / 设备签名 / 之后的一切
```

`E2E_PARAMS` 也可以通过 `GET ./e2e-params`（公开，不含秘密）预先获取，用于在登录页显示 PC 名称和身份状态。新增两种帧类型：`0x30 E2E_HELLO`、`0x31 E2E_ACCEPT`。

## 11. 兼容与迁移

| 变化 | 迁移方式 |
| ---- | -------- |
| 路径式链接到子域名链接 | Hub 开启子域名模式后，旧链接自动 301 到新链接。PC 页面显示新链接和二维码；已保存到手机主屏的旧链接仍然可以使用，经由重定向 |
